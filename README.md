# ship-driver

`ship-driver` — самодельный драйвер корабельной шины для контроллеров **Wiren Board**. Он берёт
под себя все четыре LoRa‑передатчика (`/dev/ttyMOD1..4`) — это четыре независимых равнозначных
канала. На каждом работает своя копия одного и того же «автомата корабля»: опрашивает борт по
Modbus (модули `pwm8a04` на адресах 11/12/13 и ИБП `WB‑UPS‑v3` на адресе 10), подмешивает в шину
команды плеера DFPlayer, ведёт машину режимов, держит расписание опроса и снижает ток заряда,
когда батарея греется. Всё, что происходит на борту, видно в MQTT — как устройства `boat1..4`.

Кроме кораблей драйвер обслуживает **беспроводные зарядные станции** `charger1..N`: включает реле
передатчика и магнитов фиксации, следит за током передатчика. С зарядками он общается по Modbus
RTU через TCP‑шлюз (EBYTE serial server) — отдельно от корабельной LoRa‑шины.

На корабельной шине он заменяет собой штатные `wb-mqtt-serial` и `rs485-arbiter`.

**Дальше — два больших раздела, под две разные задачи:**

- **[🛰 Удалённое управление по MQTT](#-удалённое-управление-по-mqtt)** — если вы управляете

  команды; в железо вникать не нужно.
- **[🔧 Устройство, монтаж и настройка](#-устройство-монтаж-и-настройка)** — если вы собираете,
  ставите и настраиваете драйвер на контроллере: как он устроен, как всё подключено, конфиг,
  установка, выпуск релиза.

# 🛰 Удалённое управление по MQTT

Здесь собрано всё, что нужно для удалённого управления — про железо и установку можно не думать.

**Как устроены топики.** Прочитать значение можно из `/devices/<устройство>/controls/<контрол>`, а
чтобы отдать команду — пишем в тот же топик с суффиксом `/on`. Устройств три вида: `boat1..4`
(корабли), `charger1..N` (зарядки) и `ship_setup` (проводная преднастройка — она относится к
разделу настройки).

## Корабли `boat1..4`

Устройство `boatN` появляется **только для реально подключённых каналов** — там, где есть порт
`/dev/ttyMODn` и LoRa‑модем отвечает. Состав борта всегда один и тот же: 4 мотора и 5 огней. Пока
канал не на связи (режим SEARCH) или выключен (OFF), на дашборде видны только `enabled`, `mode` и
`ship_number` — остальные контролы прячутся и возвращаются, как только борт выходит на связь.

| Контрол | Доступ | Назначение |
|---|---|---|
| `enabled` | зап. | канал вкл/выкл (1/0) |
| `mode` | чт. | текущий режим (см. ниже) |
| `battery_current` / `battery_voltage` / `battery_temperature` / `charge_level` | чт. | телеметрия ИБП |
| `input_voltage` | чт. | входное напряжение ИБП, В (опрос 5 с, вместе с током) |
| `rssi` / `comms_errors` / `link_quality` | чт. | качество LoRa‑связи активного борта: RSSI (дБм), промахов чтения за 5 мин, % успешных чтений |
| `link_score` | чт. | **общая оценка связи 0…100** — свёртка потерь, качества, сигнала и задержки в одно число (см. «Оценка связи») |
| `read_failures` | чт. | **реально потерянные чтения** за 5 мин — отказы после всех повторов (в отличие от `comms_errors`, где считается каждая попытка) |
| `err_timeout` / `err_frame` | чт. | подпись отказов за 5 мин: «не пришло ни байта» (потерян пакет) против «обрывок / чужой кадр / битый CRC» (фрейминг, тайминги) |
| `course` / `roll` / `pitch` | чт. | углы борта, ° — курс (−180…180), крен, дифферент (датчик считает их сам) |
| `gyro_x` / `gyro_y` / `gyro_z` | чт. | угловые скорости, °/с (`gyro_z` = скорость поворота по курсу) |
| `accel_x` / `accel_y` / `accel_z` | чт. | ускорения в системе борта, g (в них входит и проекция силы тяжести) |
| `mag_x` / `mag_y` / `mag_z` | чт. | магнитометр, сырые единицы — по ним видно искажения поля (моторы, магниты площадки) |
| `q0` … `q3` | чт. | кватернион ориентации (единичный) — для расчётов без разрывов и вырождений |
| `sensor_temp` | чт. | температура датчика, °C |
| `retry_fixed` / `lat_p95` | чт. | промахов, вылеченных повтором, и латентность чтения p95 (мс) |
| `back_left` / `front_left` / `back_right` / `front_right` | зап. | моторы (Back/Front × Left/Right), 40–80 % (40 = холостой) |
| `nav_lights` / `morse_lamp` / `deck_lights` / `cabin_light1` / `cabin_light2` | зап. | свет, 0–100 % |
| `mp3_track` | зап. | плеер: 0 = стоп, 1–15 = трек |
| `mp3_volume` | зап. | плеер: громкость 0–30 |
| `ship_number` | зап. | номер корабля (= LoRa‑адрес) — переключает канал на этот корабль и делает **полную реинициализацию** (холостой + переарм ESC, газ прежнего борта не наследуется) |

Частоты ШИМ, тока заряда и параметров LoRa (канал, air‑rate, мощность) на дашборде `boatN` нет —
всё это живёт в конфиге контроллера.

```sh
mosquitto_pub -t /devices/boat1/controls/front_right/on -m 50   # мотор перёд-право = 50%
mosquitto_pub -t /devices/boat1/controls/nav_lights/on  -m 100  # ходовые огни = 100%
mosquitto_pub -t /devices/boat1/controls/mp3_track/on   -m 3    # играть трек 3
mosquitto_pub -t /devices/boat2/controls/ship_number/on -m 23   # канал 2 -> корабль №23 (сразу)
mosquitto_sub -t /devices/boat1/controls/mode                   # текущий режим
```

### Режимы (`mode`)

| Режим | Когда | Что делает |
|---|---|---|
| **SEARCH** | корабль не на связи | непрерывно зондирует эфир; поймал ответ → инициализация → рабочий режим |
| **SAILING** | пришла любая команда управления | сбрасывает таймер 30 с (команды плеера режим не меняют) |
| **CHARGING** | 30 с без команд и ток батареи > 0 | драйвер держит полный ток заряда (2000 мА); тепловую защиту делает **сам WB‑UPS‑v3** — заряд блокируется при t АКБ > +50 °C (и < +5 °C) |
| **IDLE** | 30 с без команд и ток ≤ 0 | дрейф на батарее |
| **OFF** | `enabled = 0` | порт закрыт, эфир не трогается |

Из любого режима драйвер уходит в **SEARCH**, как только корабль перестаёт отвечать (два промаха
подряд). По умолчанию все 4 канала включены; и состояние вкл/выкл, **и заданный `ship_number`**
переживают перезагрузку контроллера.

### Номер корабля (`ship_number`)

У всех кораблей на одной радио‑частоте Modbus‑адреса одинаковые, поэтому на канале в каждый момент
можно разговаривать только с одним бортом — какой именно, задаёт **номер корабля** (он же
LoRa‑адрес приёмника). Стоит записать новое значение в `ship_number`, и канал мгновенно
переключается на нужный корабль: драйвер прописывает адрес в модем, берёт из конфига разводку
моторов и света именно этого корабля и через короткий SEARCH **инициализирует его заново** (частота
ШИМ и холостой газ). Раньше без этого шага при двух кораблях на одном канале второй мог не получить
`FREQ` и холостой газ — и тогда его моторы не заводились, хотя свет работал.

### Матрица опроса (период чтения телеметрии)

| Параметр | SEARCH | SAILING | IDLE | CHARGING |
|---|---|---|---|---|
| Ток батареи + вх. напряжение ИБП | ~0.8 с | 2 с | 5 с | 5 с |
| Температура АКБ | — | 60 с | 60 с | 10 с |
| Процент заряда | — | 60 с | 60 с | 20 с |
| Моторы + свет (обратная сверка, блочное чтение) | — | 30 с | 60 с | 30 с |
| Проверка частоты ШИМ (авто-восстановление 400 Гц) | — | 10 с | 10 с | 10 с |

А вот команды управления (моторы, свет, плеер) применяются сразу же, в обход расписания.

**Надёжность чтения.** Связь идёт по радио (LoRa), одиночные потери пакетов случаются. Поэтому каждое чтение при промахе **повторяется** (`read_tries`, по умолчанию 2 попытки) — транзиентный сбой маскируется в том же цикле, значение остаётся свежим. «Ошибка чтения» (красный контрол на дашборде) остаётся только для реальной потери связи. Качество линка видно в контролах `rssi` (сила сигнала), `comms_errors` (сырых промахов за 5 мин) и `link_quality` (% успешных чтений) — они отражают тот корабль, что сейчас на канале.

В SEARCH (борт не на связи) неответ — это **не** ошибка связи, а «борта здесь нет»: такие зондирования не повторяются, не попадают в счётчики и не пишутся в журнал.

### Оценка связи `link_score` (0…100)

Смотреть на пять сырых счётчиков одновременно неудобно: RSSI может быть отличным, а данные при этом
теряться (и наоборот — слабый сигнал ещё не значит проблему, если ретрай всё вытягивает). Поэтому
драйвер сворачивает их в **одно число 0…100**, где 100 — идеал. Считается там же, где и счётчики
(в конце каждого цикла опроса тока), поэтому лишнего обмена по шине не создаёт.

**Как получается оценка.** Каждый показатель переводится в свою подоценку 0…100, пороги взяты из
измеренной нормы борта (RSSI ≈ −53 дБм, `link_quality` ≈ 96.6 %, `read_failures` = 0, `lat_p95` ≈ 117 мс):

| Показатель | Что означает | Как переводится в баллы | Вес |
|---|---|---|---|
| `read_failures` | **реальная потеря данных** (отказ после всех повторов) | `100·e^(−n/12)`: 0 → 100, 1 → 92, 2 → 85, 5 → 66, 10 → 43 | 0.45 |
| `link_quality` | доля удачных попыток чтения | 100 % → 100, 95 % → 75, 90 % → 50, ≤ 80 % → 0 | 0.25 |
| `rssi` | запас по уровню сигнала | −50 дБм → 100, −75 → 60, −90 → 25, ≤ −100 → 0 | 0.20 |
| `lat_p95` | **рост** задержки (не сама величина) | ≤ 250 мс → 100, 400 → 75, 600 → 42 | 0.10 |

Две калибровки специально «мягкие», и вот почему (проверено на живых данных 08.08):

- **Потери.** Одна неудачная пара попыток за 5 минут — это ≈ 0.3 % чтений (их в окне ~370), и значение
  обновится через 5 с следующим циклом. Первая версия шкалы (`e^(−n/3)`) роняла индекс на 13 пунктов
  за единственную потерю, из‑за чего 39 % времени он висел ниже 90 при полностью здоровом канале.
  Теперь тревога наступает там, где потери **копятся**, а не от единичной.
- **Задержка.** Базовая `lat_p95` зависит от состава борта: без датчика ≈ 95 мс, с инклинометром
  ≈ 220 мс (длинное блочное чтение 33 регистров). Штраф с порога 100 мс означал бы вечный минус
  ~24 пункта просто за наличие датчика, поэтому штраф считается только **выше 250 мс** — то есть за
  реальный рост задержки.

Дальше — взвешенное среднее, **плюс ограничение сверху**: итог не может превышать «оценку потерь + 20».
Это главное свойство формулы — **реальные потери всегда тянут индекс вниз**, даже когда сигнал
отличный. Иначе борт у самого причала (−40 дБм) показывал бы «отлично», теряя при этом данные.

Если какого‑то показателя ещё нет (например, RSSI до первого успешного пакета), его вес просто
исключается из суммы — оценка считается по оставшимся.

**Как читать:** ≥ 90 — отлично, 75…90 — хорошо, 50…75 — слабо, < 50 — плохо. Для ориентира при
нынешней калибровке: здоровый линк (потерь нет, `link_quality` ≈ 98, RSSI −45) даёт ≈ 97–98;
одна потеря за 5 минут — 94; две — 91; провал в «слабо» наступает при 5+ потерях за окно.

Сырые счётчики никуда не деваются: они по‑прежнему в MQTT и в истории, и именно по ним разбираются
причины, когда индекс проседает. `link_score` — это «светофор», а не замена диагностике.

**Блочная запись (Modbus func 16).** Регистры скважности внутри модуля идут подряд, поэтому драйвер пишет их **одним кадром на модуль**: оба мотора модуля — одна транзакция вместо двух, инициализация борта — 6 транзакций вместо 18. Поддержка проверяется автоматически при первой блочной записи; если модуль func 16 не понимает, драйвер молча откатывается на поштучную запись (в журнале будет строка об этом).

**Диагностика природы отказов.** Не всякий промах — «плохое радио». Драйвер классифицирует каждую неудачную попытку: `err_timeout` (не пришло ни байта — так выглядит потерянный пакет) и `err_frame` (обрывок кадра, чужой slave/func, битый CRC — так выглядят тайминги и мусор в буфере). Плюс `retry_fixed` (сколько промахов вылечил повтор), `lat_p95` (латентность) и `read_failures` (отказы после всех попыток = реальная потеря данных). Каждый промах пишется в журнал строкой с типом, адресом, мгновенным RSSI и полученными байтами — этого достаточно, чтобы отличить эфир от протокола, не выходя на воду.

**Мощность передатчиков и взаимное глушение (важно для нескольких бортов).** Береговые модемы стоят рядом, поэтому передатчик одного канала **глушит приёмник** соседнего независимо от расстройки по частоте: полезный сигнал с борта приходит примерно −55 дБм, а сосед светит в сантиметрах. На 22 дБм это давало ~6 % промахов на рабочем канале, стоило трём другим каналам работать. На **10 дБм глушение исчезает полностью** (проверено A/B: 0 промахов при работающих соседях против 36 за 15 минут на 22 дБм), а запас над чувствительностью остаётся огромным. Поэтому по умолчанию в конфиге стоит `power: 10`; поднимать стоит только если не хватает дальности, и тогда — вместе с разносом антенн (≥ 20–30 см) и распределением активных бортов по самым далёким друг от друга каналам (14 и 19).

Если промахи всё же окажутся «фреймингом», есть параметр **«Пауза перед транзакцией, мс»** (`tx_gap_ms`, по умолчанию 0): даёт модему домолчать и переключить TX→RX перед следующим запросом.

## Зарядки `charger1..N`

Береговые беспроводные зарядные станции. Каждая появляется в MQTT отдельным устройством `charger<N>`
(с заголовком `Charger 1…N`) и управляется теми же командами с суффиксом `/on`.

| Контрол | Доступ | Назначение |
|---|---|---|
| `transmitter` | зап. | передатчик зарядки вкл/выкл (1/0) |
| `magnets` | зап. | магниты фиксации судна вкл/выкл (1/0) |
| `transmitter_current` | чт. | ток передатчика, А |

```sh
mosquitto_pub -t /devices/charger1/controls/transmitter/on -m 1   # передатчик вкл
mosquitto_pub -t /devices/charger1/controls/magnets/on     -m 1   # магниты вкл
mosquitto_sub -t /devices/charger1/controls/transmitter_current   # ток передатчика
```

> При старте драйвер ничего не переключает — он лишь **показывает** фактическое состояние реле зарядки.

# 🔧 Устройство, монтаж и настройка

Все настройки лежат в одном файле **`/etc/ship-driver.conf`** (JSON). Проще всего править его прямо
из веб‑интерфейса WB: **Настройки → Конфигурационные файлы → «Ship Driver»** (форму рисует схема
`wb-mqtt-confed`). Сохранили — и сервис сам перезапустится.

## Принцип работы

Корабли на одном канале драйвер различает по **номеру корабля** (это LoRa‑адрес приёмника, см.
[«Номер корабля»](#номер-корабля-ship_number)). При старте он приводит модем в соответствие с
конфигом — конфиг тут главный (**config‑authoritative**): читает регистры и, если они разошлись,
переписывает целиком (адрес, канал, air‑rate, мощность и reg5). Адрес берёт из сохранённого
`ship_number`, а если его нет — из конфига; канал, air‑rate и мощность — всегда из конфига. Сам
адрес можно менять на лету, контролом `ship_number`.

Корабль считается **онлайн**, если ответило хотя бы одно из четырёх Modbus‑устройств: либо UPS по
току (адрес 10), либо любой из pwm8a04 по регистру частоты (11/12/13). Поэтому борт находится
**даже при выключенном UPS** — по pwm; просто телеметрия батареи будет пустой.

Как только канал выходит в онлайн, драйвер решает по состоянию pwm‑модулей, что делать:
- модули **ребутнулись** (частота слетела с 400) **или** это была **смена корабля** → полная
  инициализация: мощность 0 → частота ШИМ 400 → моторы в холостой (40) + свет из конфига (взвод ESC);
- модули **живы** (держат 400), а был лишь короткий провал связи → драйвер **не сбрасывает газ**, а
  восстанавливает последний заданный (resume) — чтобы борт на ходу не «дёргался» из‑за радио‑икоты.

Уход в оффлайн (после нескольких промахов подряд) и возврат на связь теперь **пишутся в журнал**
(причина + длительность разрыва). Состояние вкл/выкл каналов и `ship_number` хранится в
`/etc/ship-driver-state.json`.

**Самопроверка частоты ШИМ** (группа `freq_check`, каждые 10 с). Драйвер читает частоту каналов
pwm8a04, и если она слетела в дефолт (не 400 Гц) — значит модуль перезагрузился, обычно от просадки
питания на броске тока моторов. Такой модуль остаётся «онлайн», но его ESC уже не взведены, поэтому
одной частоты тут мало: моторы всё равно не заведутся (а свет при этом работает). Поэтому драйвер
**сам гонит борт в оффлайн и инициализирует заново** — частота 400, взвод ESC, холостой газ (в
журнале: `freq drift … форсирую реинициализацию`). Проверка частая (раз в 10 с) как раз затем, чтобы
такой браунаут лечился за секунды и без ручного вмешательства — без ухода в SEARCH и смены `ship_number`.

Обратную сверку моторов и света (что реально записано в модуле против того, что мы задавали) драйвер
делает **блоком** — один Modbus‑обмен на модуль (регистры 112–114), а не по каналу за раз.

## Датчик курса (WT901C485 / JY‑901)

На борту может стоять инклинометр **WitMotion WT901C485** — он висит на той же бортовой шине, что УПС и pwm‑модули (по умолчанию Modbus‑адрес **14**, 9600). Модуль сам сводит акселерометр, гироскоп и магнитометр своим фильтром и отдаёт **готовый угол**, интегрировать ничего не нужно: драйвер читает **весь блок `0x34–0x54` одной транзакцией** (33 регистра, ~220 мс): ускорения, гироскоп, магнитометр, углы, температуру и кватернионы — и публикует их отдельными контролами. На дашборд выведен только **`course`**; остальное копится в истории для разбора.

Настройки — **в блоке своего корабля** (Настройки → Ship Driver → **Корабли → Список кораблей → Корабль №N → «Датчик курса»**, сразу после «Моторов»), потому что датчик стоит не на каждом борту: включение, Modbus‑адрес и **инверсия** (если датчик смонтирован зеркально/вверх ногами, вращение читается в обратную сторону). Период опроса задаётся в матрице опроса полем «Курс»: по умолчанию 1 с в SAILING и 10 с в остальных режимах.

Датчик стоит не на всех бортах, поэтому опрос **самоотключается**: после трёх неудач подряд драйвер перестаёт его дёргать для этого борта и пишет строку в журнал (чтобы не плодить ложные ошибки чтения). Проверка возобновляется при инициализации борта — то есть при смене `ship_number` или новом выходе на связь.

> На дашборде показан только курс — для управления остального не нужно; но всё сырьё пишется в историю, чтобы потом разобрать динамику (разгон, рыскание, искажения магнитного поля). Абсолютная привязка курса к северу требует калибровки магнитометра: рядом BLDC‑моторы и магниты фиксации, они искажают поле, поэтому пока курс отсчитывается от произвольного нуля датчика.

## Подключение света (выходы платы OUT1–OUT5)

На плате пять световых **выходов** `OUT1…OUT5`. Коммутирует их сборка Дарлингтона **ULN2003A**
(U6): это ключи с открытым коллектором — они пропускают «втекающий» ток, то есть замыкают выход на
землю. На входы ULN приходит ШИМ 5 В с каналов `pwm8a04`. Нагрузку (лента или лампа) вешают между
**общим +12 В платы** и нужным выходом `OUTx`; «+12 В» выведено на тех же разъёмах рядом с
выходами, а общий вывод ULN (COM) заведён на +12 В — для защитных диодов.

Весь свет разведён через **три модуля `pwm8a04`** (Modbus‑адреса `a11 / a12 / a13`) и **два выходных
разъёма** платы:

> ⚡ **Выходы 4 и 5 — сдвоенные:** на каждом параллельно работают **два** ключа ULN, так что они
> тянут примерно **вдвое больший ток** — вешай на них нагрузки помощнее.

**Токи (ULN2003A):**

- Выходы **1–3** (одиночный ключ) — до **~500 мА** длительно (пик 600 мА).
- Выходы **4 и 5** (два ключа параллельно) — до **~1 А**.
- Напряжение нагрузки до 50 В (на плате +12 В); падение на ключе `VCE(sat)` ≈ 1.1–1.6 В (греется).
- **Суммарно по корпусу** мощность ULN ограничена (≈ 1 Вт при 25 °C), поэтому держать все выходы на
  максимуме одновременно нельзя — работает деретинг по числу открытых ключей и по температуре.
  ШИМ со скважностью меньше 100 % снижает средний нагрев.

**Как подключать.** Плюс нагрузки — на **+12 В** платы, минус — на нужный выход. Яркость
регулируется ШИМ 0–100 % через контрол света (`nav_lights` … `cabin_light2`). Мощную нагрузку вешай
на сдвоенные выходы **4/5**, а если и этого мало — ставь внешний MOSFET.

## Зарядные станции — железо

Береговая станция подключена через **шлюз Modbus‑RTU‑over‑TCP** (прозрачный EBYTE serial server,
`host:port`) — отдельно от корабельной LoRa‑шины. Из железа на станции: передатчик беспроводной
зарядки **XKT‑801** и **магниты фиксации** судна. Они сидят на **разных каналах** реле
**WB‑MRM2‑mini** (реле нормально‑замкнутые, поэтому в конфиге для них включена «инверсия»). Ток
передатчика снимается как падение на шунте и измеряется модулем **WB‑MAI6** (ток = напряжение,
делённое на сопротивление шунта).

Станции можно вешать как угодно: несколько на один шлюз (тогда они делят TCP‑соединение) или каждую
на свой; и один WB‑MAI6 может обслуживать сразу несколько станций — по разным входам `IN`. Про
управление по MQTT — см. раздел [«Зарядки `charger1..N`»](#зарядки-charger1n).

## Конфигурация — `/etc/ship-driver.conf`

Редактируется в вебе (**Настройки → Конфигурационные файлы → «Ship Driver»**) или прямо в файле.
Из чего он состоит:

- **Основное:** скорость шины (список), таймаут ответа, ток заряда (тепловую защиту заряда
  делает сам WB‑UPS‑v3, в конфиге её нет), значения инициализации, пределы интерфейса (моторы/трек),
  матрица опроса (+ «таймаут без команд», «промахи до SEARCH», «повторов чтения»), «каналы включены при старте».
- **Радио:** план MOD1–4 — канал / air‑rate / адрес / мощность каждого передатчика.
- **Корабли:** «По умолчанию» (общие `air_rate` + `power`, резервная разводка и датчик) и «Список
  кораблей» — каждый по своему **номеру (= LoRa‑адрес)**: LoRa‑канал, разводка моторов/света
  → ШИМ (адрес + канал) и **свой «Датчик курса»** (есть ли он на борту, его адрес, инверсия).
- **Зарядки:** список зарядных станций. У каждой — свой TCP‑шлюз (`host:port`), выходы реле
  **«Передатчик»** и **«Магниты фиксации»** (адрес реле + канал K + инверсия для NC) и датчик
  тока **WB‑MAI6** (адрес + вход `IN` + сопротивление шунта). Имена устройств — `Charger N`.

Канал LoRa выбирается из списка с частотами; разрешённые ГКРЧ помечены `✓ ГКРЧ`
(CH14/16/17/19), остальные — `⚠ вне ГКРЧ`. Захардкожены: база частоты 850.125 МГц, профиль
E220 (UART 9600, subpkt128, RSSI), макс. громкость, пределы контролов, дефолты дашборда.
RU/ГКРЧ‑каналы: CH14 = 864.125, CH16 = 866.125, CH17 = 867.125, CH19 = 869.125 МГц.

## Дашборд «Ship Setup (RS485‑1)» — преднастройка корабля по проводу

Это MQTT‑устройство `ship_setup` — им прошивают LoRa‑модем корабля через порт `/dev/ttyRS485-1`.
Вручную задаются два поля — **«Номер корабля» (`ship_number`)** и **«LoRa канал» (`LoRa_channel`)**;
всё остальное только показывает состояние и запускает действия:

- `ship_number` / `LoRa_channel` — задаются вручную; `LoRa_address` — дубль номера (чтение);
  `LoRa_freq` и `Band (GKRCh)` — частота и диапазон по выбранному каналу (пересчитываются сразу);
- **«Read»** (`LoRa_read`) — читает 9 байт регистров подключённого модема и показывает все
  декодированные параметры: адрес, канал, air‑rate, мощность, LBT, UART, субпакет, RSSI эфира/в
  пакете, режим TX, WOR, версия, `raw (9 bytes)` + строка `LoRa default` для сравнения;
- **«Write»** (`LoRa_apply`) — пишет в модем заданные номер и канал (полный дамп регистров);
- результат операции (OK/ошибка) — в журнале: `journalctl -u ship-driver`.

По шагам: подключаем корабль к RS485‑1 → переводим его модем в режим **CONFIG** (переключателем на
плате) → задаём «Номер корабля» и «LoRa канал» → жмём **«Write»** (или «Read», чтобы проверить) →
возвращаем модем в **RUN**. После этого канал MODn с тем же каналом и скоростью подхватит корабль.

## Временно отдать шину штатному `wb-mqtt-serial` (напр., для настройки УПС)

**Проще всего — переключателем на дашборде.** Пакет ставит правило wb-rules
(`/etc/wb-rules/ship-bus-switch.js`) с виртуальным устройством **«Драйвер шины корабля»**
(`ship_bus`): там есть переключатель `ship_driver` (включён = работает `ship-driver`, выключен =
`wb-mqtt-serial`) и индикатор того, какой сервис сейчас активен. Логика идемпотентна, поэтому
перезапуск движка wb-rules сервисы не дёргает. Когда драйвер **останавливается** (мы отдаём шину
serial), он сам убирает свои дашборды `boatN` и `Ship Setup` — чистит retained‑топики; а при старте
объявляет их заново.

Можно и вручную, через `systemctl`. Вместе драйвер и `wb-mqtt-serial` работать не могут
(`Conflicts`). Для временного переключения берём `start`/`stop` **без** `enable/disable` — тогда
после перезагрузки сам вернётся `ship-driver`:

```sh
systemctl stop  ship-driver  && systemctl start wb-mqtt-serial   # отдать serial
systemctl stop  wb-mqtt-serial && systemctl start ship-driver    # вернуть драйвер
```

Благодаря `Conflicts` хватает и одной команды — запуска нужного сервиса. А если настройка затянется
и должна пережить перезагрузку, тогда уже `systemctl disable --now ship-driver` / `enable --now wb-mqtt-serial`.

## Установка на контроллер (один раз)

> **Сначала — железо.** Каждый MOD‑слот с LoRa‑модулем надо перевести в конфигурации
> Wiren Board в тип **«LoRa»** (веб: Настройки → Конфигурация Wiren Board → MODx → LoRa).
> Иначе UART слота не поднимется: `/dev/ttyMODn` не откроется (ошибка
> *Could not configure port: Input/output error*), и канал будет считаться отсутствующим —
> дашборд `boatN` попросту не появится.

Перед установкой не помешает обновить систему.

```sh
echo "deb [trusted=yes] https://ilya-koptev.github.io/ship-driver ./" | sudo tee /etc/apt/sources.list.d/ship-driver.list
sudo apt update
sudo apt install ship-driver
```

Что кладётся: сам драйвер `/usr/bin/ship-driver.py`, юнит `/lib/systemd/system/ship-driver.service`,
конфиг `/etc/ship-driver.conf` (это dpkg **conffile**, так что ваши правки переживут обновление) и
схема веб‑редактора `/usr/share/wb-mqtt-confed/schemas/ship-driver.schema.json`. Заодно
подтягиваются зависимости (`python3-serial`, `python3-paho-mqtt`, `mosquitto`; плюс рекомендуется
`wb-mqtt-confed`), а сервис включается и запускается. Если раньше драйвер стоял вручную
(`/usr/local/bin/ship-driver.py` и юнит в `/etc/systemd/system/`), пакет эту старую установку убирает.

## Обновление

```sh
sudo apt update && sudo apt upgrade
```

Обычно этого достаточно, но два момента пакет за тебя **не** делает:

**1. Конфиг может спросить про замену.** Если в новой версии поменялся шаблон `/etc/ship-driver.conf`
(добавили или изменили параметр), dpkg спросит: оставить твой файл или взять новый. **Оставляй свой** —
иначе затрёшь живой список кораблей и зарядок. При обновлении из скрипта (без вопросов) добавь
`-o Dpkg::Options::="--force-confold"`. Новые параметры из шаблона потом посмотри и внеси руками через
веб (**Настройки → Конфигурационные файлы → «Ship Driver»**).

**2. Дашборд пакет не трогает.** Дашборд «Ship Driver» и его виджеты лежат в конфиге контроллера
(`/etc/wb-webui.conf`), а не в пакете, поэтому apt их не обновляет. Новые контролы устройства
(например, `rssi`) появляются в разделе **«Устройства»** сами, но чтобы вынести их на дашборд — добавь
ячейку в нужный виджет борта вручную (правка дашборда в веб‑интерфейсе). Ссылка на страницу логов
`/logs` — это текст статуса устройства `ship_diag`, он приходит с пакетом и обновляется автоматически.

## Управление

```sh
systemctl status|restart|stop|start ship-driver
journalctl -u ship-driver -f
```

## Сбор логов (дашборд «Сбор логов корабля»)

Если с кораблём приключилось что‑то непонятное — в homeui есть устройство **«Сбор логов корабля»**
(`ship_diag`, ставится пакетом через wb-rules). Выбираешь **корабль** (Все или номер из настроенных)
и **период в часах**, жмёшь **«Собрать логи»** — драйвер собирает архив и кладёт в поле
**«Результат»** ссылку на скачивание из браузера.

Что попадает в `/var/www/logs/ship-logs-<корабль>-<время>.tar.gz`:
- журнал `ship-driver` за период (события, ошибки, `freq drift`, смены `ship_number`, charger);
- **телеметрия из wb-mqtt-db** по бортам (CSV: режим/ток/напряжение/заряд/углы по времени);
- `ship-driver.conf` + `ship-driver-state.json` + версия пакета + снимок текущих значений из MQTT.

Скачать: открыть страницу `http://<контроллер>/logs` — список архивов с кликабельными
ссылками (обновляется после каждого сбора; та же авторизация, что и homeui). Хранятся
последние 10 архивов. Можно и вручную: `ship-collect-logs <номер|all> <часов>`.

## Доступ и роли

Веб-панель открывается по логину. Ролей две:
- **operator** — дашборд «Ship Driver» и устройства: управление бортами, зарядкой, сбор логов; разделы настроек скрыты.
- **admin** — всё то же плюс настройки и конфиги (правка `/etc/ship-driver.conf`: модули LoRa, зарядки, матрица опроса).

Пользователей и роли заводят в самой веб‑панели (раздел настроек). Для оператора в управлении и
телеметрии ничего не меняется — разница только в доступе к настройкам, а они закрыты под `admin`.

Внешнее управление по MQTT идёт через порт `1883` и ограничено топиками корабля (`boat*`, `charger*`,
`ship_*`) — остальные топики контроллера на этом порту закрыты. Подробности — в [MQTT-API.md](MQTT-API.md).

## Релиз новой версии (мейнтейнеру)

1. Правишь драйвер (`ship-driver.py`) / схему (`ship-driver.schema.json`) / конфиг / доки.
2. **Поднимаешь `VERSION`** (apt обновляет только на бóльшую версию).
3. `git commit` + `git push` в `main`.
4. GitHub Action **build-and-publish-apt** собирает `ship-driver_<VERSION>_all.deb`,
   пересобирает apt‑репозиторий и публикует на GitHub Pages.
5. На контроллере: `sudo apt update && sudo apt upgrade`.

> ⚠️ Для перепубликации делай **новый коммит** (или запусти workflow через *workflow_dispatch*).
> **Не** жми «Re-run jobs» на старом прогоне — появятся дубли артефактов `github-pages`, и
> `deploy-pages` упадёт с *«Multiple artifacts named github-pages»*.

## Настройка репозитория (один раз, на GitHub)

- Репозиторий **public** (для GitHub Pages + apt по https без авторизации).
- Settings → **Pages** → Source = **GitHub Actions**.

Сейчас apt‑репозиторий идёт **без подписи** (`[trusted=yes]`). Если захочется GPG‑подпись — нужно
подписывать `Release` в workflow и раздавать публичный ключ.
